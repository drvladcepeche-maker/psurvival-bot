# План исследования APK и сетевого взаимодействия на Windows + Android Emulator

## Цель

Воспроизводимо исследовать публичное Android-приложение в эмуляторе, обнаружить используемые им сетевые домены, API-маршруты и форматы сообщений, сопоставить сетевые события с действиями в интерфейсе. Исследование ограничивается публично доступным поведением и тестовым аккаунтом, которым исследователь вправе пользоваться.

Не пытаться обходить аутентификацию, получать чужие токены/данные, обходить защиту сервера или античит. Не сохранять секреты в репозитории.

## 1. Подготовка Windows

1. Установить Android Studio: https://developer.android.com/studio
2. В Android Studio → SDK Manager установить:
   - Android SDK Platform-Tools (ADB);
   - Android SDK Platform для выбранного API level;
   - Android Emulator;
   - system image для виртуального устройства.
3. Через Device Manager создать AVD (например, Pixel с актуальным стабильным Android API) и запустить его.
4. Установить инструменты анализа:
   - JADX: https://github.com/skylot/jadx/releases
   - Apktool: https://apktool.org/
   - mitmproxy (необязательно, для разрешённого анализа HTTP(S)): https://mitmproxy.org/
   - Wireshark (необязательно, для DNS/TCP/TLS метаданных): https://www.wireshark.org/

Проверить расположение ADB. Обычно он находится в %LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe. В PowerShell можно задать переменную на текущую сессию:

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb version
& $adb devices -l
```

Для запущенного эмулятора ожидается устройство вида emulator-5554 со статусом device.

## 2. Установка приложения в эмулятор

Предпочтительно использовать официальный APK из источника разработчика или официального магазина. Сохранить исходный файл в локальной рабочей папке, не добавлять APK в Git без необходимости.

```powershell
New-Item -ItemType Directory -Force .\artifacts, .\analysis | Out-Null
Get-FileHash .\artifacts\target.apk -Algorithm SHA256
& $adb install .\artifacts\target.apk
```

Если приложение поставляется несколькими APK (split APK), использовать полный набор, полученный из легального источника, и установить через adb install-multiple. Не смешивать APK из разных версий.

Найти имя пакета:
```powershell
& $adb shell pm list packages -3
```

Посмотреть пути установленных APK:
```powershell
& $adb shell pm path com.example.app
```

Для каждого возвращённого пути можно попробовать скопировать APK:
```powershell
& $adb pull /data/app/.../base.apk .\artifacts\base.apk
```

Подставить реальный путь из вывода. Если чтение установочного пути запрещено, использовать официальный установочный APK вместо попыток повышать привилегии.

## 3. Статический анализ APK

Открыть APK в JADX GUI или выполнить:
```powershell
jadx -d .\analysis\jadx .\artifacts\target.apk
```

При необходимости декодировать ресурсы и Smali:
```powershell
apktool d .\artifacts\target.apk -o .\analysis\apktool
```

Искать по исходникам и ресурсам:
- https://, http://, baseUrl, /api/;
- Retrofit, OkHttpClient, HttpURLConnection, WebSocket, Socket;
- graphql, Authorization, Content-Type;
- сериализаторы JSON/Protocol Buffers и модели запросов/ответов;
- AndroidManifest.xml, сетевые security config и конфигурационные файлы.

Фиксировать найденное только как гипотезы до проверки фактического вызова. URL в библиотеке или неиспользуемой конфигурации не обязательно является действующим API.

## 4. Базовое наблюдение в эмуляторе

Сбросить логи и запустить запись:
```powershell
& $adb logcat -c
& $adb logcat -v threadtime > .\analysis\logcat.txt
```

Остановить запись сочетанием Ctrl+C. Для фильтрации после записи:
```powershell
Select-String -Path .\analysis\logcat.txt -Pattern 'https?://|WebSocket|OkHttp|SSL|TLS|Exception|UnknownHost'
```

Логи могут содержать персональные данные или токены. Перед добавлением отчёта в репозиторий удалить секреты и идентификаторы.

Воспроизвести отдельно каждый сценарий, используя тестовый аккаунт:
1. первый запуск;
2. вход/выход;
3. загрузка главного экрана;
4. чтение списка/профиля;
5. одно безопасное действие изменения состояния;
6. обновление экрана и повторный запуск.

Для каждого действия записать точное время, экран и наблюдаемые домены/события. Не запускать массовые запросы и не тестировать разрушительные операции.

## 5. Наблюдение за сетевым трафиком

Начать с DNS/TCP/TLS метаданных через доступные средства эмулятора/хоста. Для HTTP(S) можно настроить локальный mitmproxy только в собственной тестовой среде и только в пределах разрешённого доступа.

Запуск на Windows:
```powershell
python -m pip install mitmproxy
mitmweb --listen-host 0.0.0.0 --listen-port 8080
```

Далее:
1. Уточнить IP-адрес хоста, доступный из эмулятора; для стандартного Android Emulator обычно используется специальный адрес хоста 10.0.2.2.
2. В настройках Wi-Fi/прокси эмулятора указать прокси-хост и порт 8080.
3. Для тестового браузера/приложения, которое доверяет пользовательскому CA, следовать официальной документации mitmproxy по установке сертификата.
4. Проверить соединение на тестовом запросе, не используя реальные секреты.

Android-приложение может не доверять пользовательским CA, а также использовать certificate pinning. В таком случае не пытаться обходить эти ограничения для публичного стороннего приложения: продолжить пассивный анализ метаданных, статический анализ кода и документации разработчика. Отсутствие расшифрованного HTTP-трафика не означает, что сетевого обмена нет.

Официальные материалы: https://docs.mitmproxy.org/ и https://developer.android.com/privacy-and-security/security-config

## 6. Каталог результатов

Хранить локально и добавлять в Git только очищенные отчёты:
- analysis/apk-inventory.md — название, версия, package name, SHA-256, источник APK;
- analysis/endpoints.md — host, path, HTTP method, источник обнаружения и уровень уверенности;
- analysis/flows.md — последовательность запросов для каждого сценария;
- analysis/schemas.md — безопасно очищенные примеры форматов запросов/ответов;
- analysis/open-questions.md — неизвестные элементы и следующие проверки.

Для каждого endpoint указывать статус:
- **static candidate** — найден в коде;
- **observed** — подтверждён наблюдением;
- **documented** — подтверждён публичной документацией;
- **unverified** — назначение/доступность не подтверждены.

## 7. Шаблон записи endpoint

| Поле | Значение |
|---|---|
| Host | Домен без секретных параметров |
| Path | Путь без токенов/персональных данных |
| Method / protocol | GET/POST/WebSocket и т. п. |
| Trigger | Действие пользователя |
| Request format | JSON, protobuf, form data, неизвестно |
| Response format | JSON, protobuf, код состояния, неизвестно |
| Auth mechanism | Только тип механизма; никаких значений токенов |
| Evidence | Файл/класс/строка или дата наблюдения |
| Status / confidence | static candidate / observed / documented / unverified |

## 8. Критерии завершения

- APK и его SHA-256 зафиксированы.
- Package name и версия установлены.
- Основные сетевые библиотеки и кандидаты доменов перечислены.
- Для минимум трёх пользовательских сценариев составлена последовательность наблюдений.
- Найденные endpoints отделены от гипотез.
- Все логи и примеры очищены от токенов, cookies, личных данных и ключей.
- Неподтверждённые выводы явно отмечены; серверная логика, не содержащаяся в клиенте, не считается восстановленной.

## Безопасность и приватность

Не коммитить APK стороннего приложения без проверки лицензии и прав на распространение. Не коммитить дампы трафика, cookies, bearer-токены, пароли, приватные ключи, пользовательские идентификаторы или необработанные логи. При публикации отчёта оставлять только минимальные обезличенные сведения, необходимые для воспроизводимости.
